# exchangeservice

Микросервис контроля месячных лимитов расходов в банке: принимает расходные операции в валюте
счёта, переводит их в USD по биржевому курсу закрытия и помечает операции, превысившие месячный
лимит. Лимиты ведутся раздельно для категорий `product` и `service`.

Реализация тестового задания
`Тестовое_задание_Junior_Java_разработчика_2026.pdf`: пункты 1–6 обязательные выполнены полностью, из
необязательных сделаны 1\* (параллельный расчёт на виртуальных потоках), 3\* (Docker и compose) и
5\* (Actuator и метрики), а также 4\* (CI) и 6\* (AGENTS.md).

## Стек

Java 21, Spring Boot 4.1.1, Spring Web MVC на виртуальных потоках, Spring Data JPA, Liquibase
(schema first), PostgreSQL 17, RestClient, springdoc (OpenAPI), Testcontainers, WireMock,
REST Assured, JUnit 5, AssertJ, Lombok, logback + logstash-logback-encoder.

## Запуск

Нужен Docker (для тестов) и JDK 21. Сервис вместе с БД поднимается одной командой:

```bash
docker compose up --build
```

Docker Compose читает `.env` из корня репозитория сам, поэтому ключ и остальные параметры
достаточно положить в `.env` (файл в `.gitignore`, в репозиторий не попадает):

```dotenv
RATES_API_PROVIDER=twelvedata
RATES_API_BASE_URL=https://api.twelvedata.com
RATES_API_KEY=<ключ>
EXCHANGE_READONLY_PASSWORD=<пароль пользователя БД только для чтения>
```

Эквивалентно — переменные в сессии: `RATES_API_KEY=<ключ> docker compose up --build`.
Без ключа контейнер не поднимется: `exchange.rates.api-key` проверяется на старте (`@NotBlank`),
поэтому «здоровый» сервис, отправляющий каждую операцию в `FAILED`, невозможен.

Либо вручную, если БД уже есть: Схема создаётся Liquibase при старте, отдельная ручная
подготовка БД не нужна.

```bash
# PostgreSQL для ручного запуска сервиса
docker run -d --name exchange-db -p 5432:5432 \
  -e POSTGRES_DB=exchange -e POSTGRES_USER=exchange -e POSTGRES_PASSWORD=exchange \
  postgres:17-alpine

set -a && source .env && set +a   # Spring Boot файл .env не читает, переменные нужны в окружении
./mvnw spring-boot:run -Dspring-boot.run.profiles=dev
```

Swagger UI: <http://localhost:8080/swagger-ui.html>, OpenAPI: `/v3/api-docs`.

Готовые запросы для проверки вручную: `POSTMAN_GUIDE.md` и `POSTMAN_QUICK_TESTS.md`, коллекция
`exchangeservice.postman_collection.json`.
health-check: `/actuator/health` — детали компонентов видны всегда
(`management.endpoint.health.show-details: always`), в том числе состояние подключения к
PostgreSQL: `when-authorized` при отсутствии Spring Security не показал бы их никогда.

Тесты (нужен только установленный Docker, внешний API курсов мокается WireMock):

```bash
./mvnw test        # 183 тестов: 62 unit + 121 интеграционных
./mvnw verify      # то же + проверки сборки
```

Конфигурация задаётся переменными окружения: `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`,
`DB_POOL_SIZE`, `RATES_API_PROVIDER`, `RATES_API_BASE_URL`, `RATES_API_KEY`. Профили `dev`, `test`,
`prod` (см. `src/main/resources/application*.yaml`).

Секретов в репозитории нет: у всех таких переменных в YAML пустое или заведомо небоевое значение по
умолчанию, поэтому `grep` по отслеживаемым файлам не находит ни ключа, ни пароля. `RATES_API_KEY`
обязателен, `RATES_API_BASE_URL` должен содержать схему, а `RATES_API_PROVIDER` должен совпадать с
адаптером, объявленным в `RateClientConfig`: без этого сервис не поднимается с понятной ошибкой
конфигурации, а не «стартует здоровым и падает на каждом запросе курса».

## Часовой пояс границ месяца: UTC

Месячные границы считаются в **UTC**. Операция 2022-01-31T23:30:00+06:00 попадает в январь,
потому что по UTC это 2022-01-31T17:30Z.

Зона задана одной константой `BudgetPeriod.LIMIT_TIMEZONE`, а не настройкой: `LimitCalculator`,
`SettlementApplier`, `LimitCommandService` и запросы остатков обязаны считать месяц одинаково, и
второй источник зоны (`exchange.limit.timezone` рядом с дефолтным лимитом) давал бы возможность
разъехаться расчёту и отображению. Тесты переводят время через `TestClock`, поэтому смена зоны
была бы видна как падение граничных сценариев, а не как тихая ошибка в проде.

## Семантика лимитов

Ключевые решения, которые неочевидны из ТЗ и зафиксированы тестами:

- **Флаг кумулятивный.** `limit_exceeded` сравнивает накопленную сумму всех операций месяца «до и
  включая текущую» с лимитом, действовавшим на момент её совершения. Строгое сравнение: при
  остатке ровно 0 флаг равен `false`.
- **Лимит принадлежит паре «счёт + категория + месяц».** Операции соседнего месяца или соседней
  категории не влияют на флаг.
- **Смена лимита внутри месяца не меняет флаги более ранних операций** — они рассчитаны по лимиту,
  действовавшему тогда (п.4 ТЗ).
- **Остаток, в отличие от флага, считается от расходов всего месяца с 1-го числа**, а не от даты
  установки лимита. Это даёт остаток 900 в ТЗ: лимит 2000 USD от 10.01, расходы 500 + 600.
- **Лимит по умолчанию физически не хранится.** 1000 USD с датой в начале месяца вычисляются на
  лету, поэтому у такого лимита `id == null`.
- **Поздняя операция с ранней датой пересчитывает флаги.** Операция, дошедшая до расчёта позже
  операций с поздними датами, увеличивает накопленный итог и для них. Без пересчёта сохранённые
  флаги остались бы навсегда заниженными, и клиент получил бы неверный отчёт.
- **Смена лимита пересчитывает флаги периода.** Новый лимит не применяется задним числом, но
  меняет порог для всех более поздних операций месяца, в том числе уже посчитанных. Без
  пересчёта операция с будущей датой, рассчитанная до того, как клиент поднял лимит, осталась бы
  с устаревшим флагом навсегда: пересчитывать её было бы некому — по `occurred_at` она ещё не
  наступила. Пересчёт делает `LimitCommandService` в той же транзакции, что и запись лимита.
- **Итог по лимиту для клиента считает SQL, а не Java.** Расход и остаток периода — одна
  реализация, нативный запрос `findLimitsWithSpentAmount`. Дублировать её в `LimitCalculator` нельзя:
  две реализации одного правила расходятся, а `limit_exceeded` тогда окажется посчитан по одной,
  а показан клиенту — по другой.

## API

Два контура API разведены по URL.

Интеграция с банковскими сервисами:

| Метод | Путь | Ответ |
| --- | --- | --- |
| `POST` | `/api/v1/transactions` | `202 Accepted`, тело — транзакция в статусе `PENDING` |
| `GET` | `/api/v1/transactions/{id}` | состояние расчёта: курс, сумма в USD, флаг |
| `POST` | `/api/v1/transactions/{id}/settle` | ручной досчёт операции: `200` — посчитано, `202` — попытка предпринята, но курс недоступен |

Клиентский API:

| Метод | Путь | Ответ |
| --- | --- | --- |
| `POST` | `/api/v1/limits` | `201 Created`, установленный лимит |
| `GET` | `/api/v1/limits` | лимиты с остатком, новые первыми; лимит по умолчанию для пар с расходом — без `limit_id` |
| `GET` | `/api/v1/limits/exceeded` | превышенные транзакции с параметрами превышенного лимита; постранично: `limit` (до 500) и `offset` |

### Идентификатор операции `transaction_id`

Поле необязательное и служит ключом идемпотентности: повторная доставка операции с тем же
`transaction_id` возвращает уже принятую запись и не создаёт вторую. Формат — UUID в канонической
форме `8-4-4-4-12`; если поле не прислано или пустое, идентификатор генерирует сервис.

Непустое значение не-Uuid отклоняется с `400`, а не подменяется сгенерированным. Подмена теряла
идентификатор банка, и каждая повторная доставка той же операции превращалась в новую запись —
месячный расход удваивался, а данные не терялись только потому, что банк умел повторять запрос.
Отказ честнее потери идемпотентности: клиент знает, что его идентификатор не понят, и может
прислать корректный.

### Период в `GET /limits` и пагинация превышений

`GET /limits` возвращает все лимиты счёта — этого требует ТЗ («получение всех лимитов»), и история
смен лимитов сама по себе полезна. Но расход и остаток считаются только для текущего месяца: у
лимитов прошлых месяцев `spent_usd` и `remaining_usd` равны `null`, а `in_current_period` —
`false`. Ноль вместо `null` был бы враньём: в феврале январский лимит 1000 USD выглядел бы
нетронутым, и клиент получил бы два ответа, которые противоречат друг другу, — «осталось 5000» в
`GET /limits` и «превышен лимит 1000» в `GET /limits/exceeded`.

`GET /limits/exceeded` отдаётся постранично: `limit` (по умолчанию и не больше 500) и `offset`.
Порядок страниц — тот же, что у расчёта флагов (`occurred_at, id`), поэтому страницы не
пересекаются. Без `limit` клиент получает первую страницу, а не всю выборку: у клиента с
лихорадочным расходом превышений могут быть тысячи, и отдавать их одним ответом — это ответ,
который клиент всё равно не осилит, а сервис посчитает и отдаст целиком.

### Лимит по умолчанию в `GET /limits`

Пара «счёт + категория», по которой в текущем месяце есть расход, но клиент не устанавливал лимит,
живёт по умолчанию: 1000 USD, момент установки — первый день месяца. Расчёт применяет этот лимит и
выставляет по нему `limit_exceeded`, поэтому `GET /limits` показывает его отдельной строкой — с
`limit_sum`, `spent_usd` и `remaining_usd`. Без этой строки клиент видел бы флаги превышения и пустой
список лимитов: по какому лимиту посчитаны флаги, было бы неизвестно.

`limit_id` такой строки равен `null`: лимит по умолчанию физически не хранится, и идентификатора у
него нет. Выдуманный идентификатор был бы ссылкой на несуществующую запись. Пары без расхода в
текущем месяце дефолтной строки не получают — показывать лимит, который ничего не ограничивает,
незачем.

Строка добавляется в SQL, а не в Java: остаток и расход считает один запрос
(`findLimitsWithSpentAmount`, вторая ветка `UNION ALL`), и вторая реализация того же правила в
приложении разошлась бы с ним. Условие «лимита по паре нет в этом месяце» — то же, по которому флаг
считается: лимит принадлежит календарному месяцу, поэтому установленный в январе лимит не
применяется к февралю, а февральский расход показывается по умолчанию 1000 USD.

Расход месяца присоединяется только к лимитам того же месяца. Иначе февральский расход присоединился
бы к январскому лимиту, и два ответа об одном клиенте говорили бы разное: `GET /limits` — «осталось
3900», `GET /limits/exceeded` — «превышен лимит 1000». Лимиты других месяцев остаются в ответе как
история изменений, но с нулевым расходом и остатком, равным своей сумме. Регрессия закреплена тестом
`ExpenseApiIntegrationTest#previousMonthLimitDoesNotAbsorbCurrentMonthSpending`.

Дата установки лимита клиентом не передаётся: её проставляет сервис из бина `java.time.Clock`,
поэтому лимит нельзя «отмотать» в прошлое или в будущее. Обновление существующего лимита
запрещено (п.5 ТЗ) — новый лимит создаётся новым запросом.

Ошибки — единый формат ProblemDetail (RFC 9457), `application/problem+json`:

| Код | Когда |
| --- | --- |
| `400` | Bean Validation и нечитаемый JSON: перечень нарушений в расширении `errors`, где `field` назван так, как его видит клиент (`account_from`), а не по имени Java-компонента |
| `404` | неизвестная транзакция или лимит |
| `422` | формат верен, но значение смыслово неприемлемо, например `reason=unknown_currency` |
| `409` | состояние уже занято: `reason=limit_already_set`, лимит на этот момент установлен |
| `500` | непредвиденная ошибка, детали не раскрываются |

Точность суммы (`@Digits`) проверяется на границе API как ошибка формата (`400`), а не в сервисе
второй раз: одна проверка одного правила.

## Стратегия работы с внешним API курсов

Внешний провайдер — [Twelve Data](https://twelvedata.com), дневной интервал (`1day`), берётся
`close`, а при отсутствии торгов — `previous_close` (п.3 ТЗ).

**Обратная пара, если прямой нет.** Не все валюты котируются к USD напрямую: тенге Twelve Data
имеет только как `USD/KZT`, а `KZT/USD` отвергает с 404 `symbol is missing or invalid`. Если прямой
пары нет, провайдер берёт обратную (`USD/BASE`) и обращает курс: `1 / 448.44374 = 0.0022299341`.
Без этого операции в таких валютах висели бы в `PENDING` до `FAILED`, хотя курс у провайдера есть —
просто в обратном направлении. Обратный курс считается с `RATE_SCALE` знаками после точки: при
округлении по умолчанию тенге превратились бы в `0.00`, и сумма в USD молча уехала бы в ноль.

Запрос к внешнему API платный и медленный, поэтому курсы хранятся в собственной БД
(`exchange_rate`) и используются преимущественно: `ExchangeRateService` сначала смотрит кэш и
только потом обращается к провайдеру. Повторный запрос за ту же пару и дату не выполняется.

**Приём транзакций не зависит от доступности провайдера.** Это ключевое требование ТЗ:

1. `POST /api/v1/transactions` сохраняет транзакцию в статусе `PENDING` и сразу отвечает `202`.
   Внешний API в этом потоке не вызывается.
2. Расчёт курса и флага выполняется отдельно (`PendingSettlementScheduler`, виртуальные потоки) и
   начинается сразу: зафиксированная строка `PENDING` публикует событие приёма, и проход
   дорасчётки ставится в очередь пула расчёта. Поэтому клиент, отправивший операцию и сразу
   запросивший превышения, не ждёт `exchange.settlement.retry-delay` — флаг уже посчитан.
3. Плановый проход каждые `retry-delay` — страховка, а не основной темп: он подхватывает пачку,
   которая не уложилась в один проход, и всё, что пришло при выключенной фоновой обработке.
4. Клиент читает состояние расчёта через `GET /api/v1/transactions/{id}`.
5. Если провайдер недоступен, транзакция остаётся `PENDING` и дорасчитывается позже, пока не
   исчерпает `exchange.settlement.max-attempts` (по умолчанию 5), после чего переходит в `FAILED`.
   `FAILED` — терминальный статус, но не приговор: `POST /api/v1/transactions/{id}/settle` считает
   транзакцию заново (`200` — посчитано, `202` — курс всё ещё недоступен), флаги за ней
   пересчитываются.
5. Повторный `POST` с тем же `id` не создаёт вторую транзакцию: запись вставляется нативным
   `INSERT ... ON CONFLICT (id) DO NOTHING`, и клиент получает состояние уже принятой операции.
   Без этого отправленный дважды запрос удваивал бы расход клиента и его лимит.

Таймауты и повторы заданы явно (`exchange.rates.*`): `connect-timeout` и `read-timeout` не дают
висеть на мёртвом провайдере, а ограниченное число повторов с экспоненциальной задержкой
(`RetryingCaller`) переживает кратковременные сбои, не превращаясь в лавину повторов при
недоступности.

### Точность курса

Курс хранится с десятью знаками после точки (`NUMERIC(19, 10)`, константа
`ExchangeRate.RATE_SCALE`), а суммы — с двумя: `amount` и `limit_sum` это `NUMERIC(19, 2)`,
а `amount_usd` — `NUMERIC(30, 2)`. Последняя шире по необходимости: `amount_usd` есть произведение
`amount` на курс, и при курсе выше единицы (KWD, BHD, JOD) оно не помещается в 19 знаков.
Переполнение приводило к `numeric field overflow` на записи, то есть принятая по формату сумма
оказывалась несохранимой. Отвергать такую сумму на приёме нельзя — это потеря данных, поэтому
ширину расширила миграция `004-amount-usd-precision.sql`.

Четырёх знаков для реальных курсов к USD не хватает:

- у KZT курс около `0.0025`, округление до четырёх знаков отбрасывает до 0.5% курса: `10000.45`
  тенге превратились бы в `25.00` USD вместо `25.12`;
- курс мельче половины последнего разряда (`0.00005`) обнуляется совсем, а CHECK
  `close_rate > 0` отвергает такую запись. Валюта становится нерасчётной навсегда: транзакция
  остаётся `PENDING`, затем уходит в `FAILED` и больше не дорассчитывается. Сюда попадают VND
  (`0.0000391`), IDR (`0.0000618`), KRW.

Поэтому цена, которая не положительна, курсом не считается: `TwelveDataRateProvider` не пишет
такую запись в кэш, а возвращает пустой результат, и срабатывает штатный путь отложенного расчёта.
Сбой записи курса в БД не ловится вместе со сбоем внешнего API: нарушение ограничения нашей схемы
выглядело бы в логе как недоступность биржи, и транзакция ушла бы в `FAILED` без видимой причины.

Миграция `003-rate-precision.sql` расширяет тип колонок; PostgreSQL переписывает таблицы под
`ACCESS EXCLUSIVE`, поэтому её выполняют в окно обслуживания. Уже сохранённые курсы остаются с
четырьмя знаками: потерянную при прежнем округлении точность переносом типа не вернуть — при
необходимости курсы запрашивают заново, а решение об очистке кэша принимает оператор.

## Наблюдаемость

Actuator отдаёт `/actuator/health` (детали компонентов всегда) и `/actuator/prometheus`.

Метрики Micrometer по работе с внешним API курсов — главный эксплуатационный сигнал, потому что
именно там платные и медленные запросы:

| Метрика | Смысл |
| --- | --- |
| `exchange.rates.provider.duration` | длительность вызовов внешнего API вместе с повторами |
| `exchange.rates.provider.requests{outcome=miss\|failure}` | сколько раз пошли в провайдер и чем закончилось |
| `exchange.rates.cache.lookups{outcome=hit\|miss\|unresolved}` | попадания и промахи собственной БД |

Резервный курс берётся не из последней записи в кэше, а из последней **не старше**
`exchange.rates.max-fallback-age` (по умолчанию 7 дней). Курс недельной давности — это уже другой
рынок, и молча подставить его в лимит опаснее, чем вернуть ошибку расчёта: транзакция уходит в
`FAILED`, попадает в отчёт по попыткам и ждёт либо операции, либо ручного дорасчёта.

Рост доли `outcome=unresolved` означает, что транзакции копятся в `PENDING`; рост `miss` при
нормальном `hit` означает поток операций по датам, которых ещё нет в кэше.

Счётчик попыток `settlement_attempts` растёт одной командой `UPDATE`, а не чтением и записью из
Java: инкремент в Java конкурентным попыткам не виден, и две реплики сервиса (или два прохода
планировщика) затирали бы попытку друг друга — счётчик зависал бы, а транзакция не доходила бы до
`FAILED` никогда. Тем же `UPDATE` рассчитанная транзакция не переводится обратно в `FAILED`: курс и
сумма у неё уже заполнены, и такой перевод нарушил бы CHECK-ограничение схемы.

**Что считается попыткой.** Попытка — это проход расчёта, а не причина сбоя, поэтому счётчик растёт
и когда курс не пришёл, и когда расчёт упал, и когда упало получение курса на нашей стороне
(например, запись курса в кэш нарушила ограничение схемы). Единственное исключение — отмена
дорасчёта из-за остановки сервиса: она бросает `RateCallCancelledException`, и попытка не
засчитывается, потому что до расчёта дело не дошло. Раньше прерванный повтор выглядел как
недоступность биржи, и при `max-attempts: 1` один перезапуск сервиса переводил нормальные
транзакции в `FAILED`.

**Пачка берётся атомарно.** Планировщик не читает пачку обычным `SELECT`, а забирает её через
`claimPending`: `SELECT ... FOR UPDATE SKIP LOCKED` в одной транзакции с инкрементом счётчика. Две
реплики сервиса (или два прохода планировщика) не разбирают одну пачку дважды — иначе счётчик попыток
рос вдвое быстрее, транзакции достигали `FAILED` раньше срока, а внешний API получал двойные платные
вызовы. Попытка засчитывается при взятии пачки, а не по исходу расчёта: сбой между взятием и
расчётом не оставит транзакцию с незасчитанной попыткой. Отменённый дорасчёт снимает засчитанную
попытку, поэтому остановка сервиса не «съедает» попытки.

Ручной дорасчёт (`POST /api/v1/transactions/{id}/settle` → `TransactionIntakeService.settle`)
считает попытки по тем же правилам, что и планировщик, и возвращает состояние транзакции **после**
попытки: снимок, взятый до неё, утверждал бы `PENDING` для транзакции, которая попыткой только что
достигла `FAILED`. Эндпоинт существует потому, что `FAILED` иначе недостижим в эксплуатации:
дорасчёт существовал бы только вызовом сервиса из теста.

**Проход один за раз, но транзакция не ждёт планового.** Параллельные проходы не нужны: дедупликация
курсов по паре «валюта + дата» видит только свой проход, и два прохода отправили бы платные запросы
дважды. Взамен проход, увидевший запрос во время работы, делает ещё один круг — операция, принятая
после взятия пачки, уходит в следующий круг, а не в `retry-delay`. Между проходами платные запросы
не повторяются: курс уже лежит в `exchange_rate` (проверено тестом: десять операций одной пары
«валюта + дата» — один запрос к внешнему API).

Пауза между плановыми проходами и размер пачки заданы конфигурацией: `retry-delay` и
`batch-size` в `exchange.settlement`. Обе настройки объявлены в `application.yaml` один раз —
дублировать их в коде нельзя, иначе забытое обновление одного из двух значений молча меняет
поведение расчёта.

Логи событий делового процесса идут в SLF4J: приём операции (включая повтор по тому же `id`),
применение курса, пересчёт флагов при смене лимита, отказ от протухшего курса, исчерпание попыток.
В профиле `prod` (его включает `docker-compose.yml`) вывод JSON — `logback-prod.xml` с
`logstash-logback-encoder`, включая `application` в каждой записи.

**Чего нет и почему.** Логирования тел запросов и ответов (Logbook) в сервис не подключено:
актуальная версия библиотеки (3.12.x) собрана под Spring Boot 3, а проект на Boot 4.1.1, где
`WebMvcAutoConfiguration` больше не поставляется `spring-boot-autoconfigure` и её автоконфигурация
не поднимется. Своими руками такой фильтр писать не стоит: он повторит то, что делает `RestClient`
и Micrometer, а через год разойдётся с ними. Если задача вырастет в аудит HTTP-обмена, Logbook
подключится сам, когда выйдет версия под Boot 4 — трогать домен и порты для этого не нужно.

## Многопоточность

Транзакции одного клиента приходят параллельно, и два запроса не должны «увидеть» один и тот же
остаток лимита (п.4 ТЗ).

Расчёт выполняется в транзакции БД и начинается с пессимистичной блокировки периода:
`SELECT ... FOR UPDATE` на строке-замке `spend_period_lock` для пары «счёт + категория + месяц».
Блокировка берётся **до** чтения накопленной суммы, поэтому второй поток ждёт и считает уже
обновлённые расходы. Строка-замок создаётся лениво при первом расчёте периода.

Приём транзакции (`POST /api/v1/transactions`) эту блокировку **не** берёт: он только вставляет
строку `PENDING`, в накопленную сумму не входящую. Иначе приём вставал бы в очередь за расчётом
того же периода и удерживал соединение пула, пока ждёт, — то есть отнимал соединение у расчёта,
который за этой блокировкой стоит, и при неудачном соотношении пула и параллелизма выедал пул
целиком: страдали бы уже все запросы клиента, а не расчёт. Проверено тестом
`ConcurrentSettlementIntegrationTest#intakeDoesNotWaitForSettlementPeriodLock`: при удерживаемой
блокировке периода приём всё равно возвращает `202`.

Проверено тестом `ConcurrentSettlementIntegrationTest`: 30 операций в 6 потоках дают сумму ровно
3000 USD и флаги, совпадающие с кумулятивным пересчётом по всем операциям.

### Стоимость пересчёта флагов

Флаг кумулятивный, поэтому каждой операции нужна сумма всех предшествующих за месяц. Перечитывать
весь месяц на каждый расчёт нельзя: пачка из n операций одного периода тогда читает его n раз.
Поэтому расчёт берёт **суффикс периода** — операции начиная с расчётной, — а накопленную сумму до
нее спрашивает у базы одной строкой (`sumResolvedInPeriodBefore`). У стоящих раньше накопленный итог
не меняется, значит и флаги их не меняются.

Замер на одной машине, один счёт, одна категория, операции по 10 USD в пределах месяца:

| Операций | Раньше (весь период на каждый расчёт) | Теперь (суффикс) |
| --- | --- | --- |
| 100 | 3.0 с | 3.1 с |
| 400 | 6.5 с | 6.8 с |
| 800 | 16.4 с | 11.5–15.3 с |
| 1600 | ~45 с (экстраполяция) | 24.3 с |

Разница на 100–400 операциях незаметна: там стоимость задаёт фиксированная работа на операцию
(своя транзакция, блокировка периода, запись). Разница видна там, где квадратичность успевала
потреблять время, — и, главное, в масштабировании: раньше удвоение пачки стоило 2.5×, теперь 1.6×.
Проверяется тестом `SettlementCostIntegrationTest`: он же сверяет, что накопленная сумма из SQL
совпадает с посчитанной в Java, а `LimitCalculatorTest#suffixWithSeededTotalMatchesWholePeriod`
доказывает, что суффикс с начальным итогом даёт ровно те же флаги, что и весь период.

Флаг кумулятивный, поэтому каждой операции нужна сумма всех предшествующих за месяц. Если считать
эту сумму заново для каждой операции, пересчёт становится квадратичным: месяц с 50 000 операций —
это 1,25 млрд сложений, и столько же повторяется на каждый расчёт транзакции и на каждую смену
лимита.

`LimitCalculator.computeFlags` накапливает итог одним проходом по отсортированному списку: после
сортировки стоимость линейна. Правило при этом одно: накопленная сумма операции совпадает с
`spentUpTo`, а флаг — с `isExceeded`, второй реализации расчёта не появилось. Проверено
юнит-тестами: пакетный расчёт сверяется с пооперационным на сценарии из таблицы ТЗ, а
`largePeriodIsRecalculatedWithoutQuadraticCost` ограничивает 50 000 операций пятью секундами —
старая квадратичная реализация эту границу не укладывает.

Остаточная стоимость пересчёта — линейное чтение операций периода из БД. Оно необходимо на каждый
расчёт: накопленный итог операции включает все предыдущие, а не только последние.

### П.1*: параллельный расчёт на виртуальных потоках

Досчёт пачки `PENDING` разделён на две фазы, потому что курс и флаг — это работа разной природы:
курс стоит времени ожидания сети, флаг считается в своей БД под блокировкой периода.

1. **Курсы.** `ParallelRateResolver` получает курсы для всей пачки параллельно на виртуальных
   потоках. Повторы одной пары «валюта + дата» схлопываются в один запрос к провайдеру: за месяц
   клиент присылает много операций в одной валюте, а платить за каждый HTTP-запрос нельзя. Побочный
   эффект — снятие гонки на `uc_exchange_rate_pair_date`, где два потока одновременно проверяли бы
   отсутствие строки курса.
2. **Расчёт.** `SettlementApplier` применяет уже известный курс, каждая транзакция в **своей**
   транзакции БД с блокировкой периода. Падение одной транзакции не откатывает остальные.

Ключевой момент: фаза курсов выполняется **вне** транзакции БД и **вне** блокировки. Иначе соединение
с PostgreSQL ждало бы сеть, и все расчёты одного счёта выстроились бы в очередь на замке — параллелизм
был бы только видимостью.

**Что параллельно, а что нет.** Разные периоды и разные счёты считаются одновременно. Операции одного
`(счёт, категория, месяц)` остаются строго последовательными — этого требует корректность лимита,
и она важнее скорости. Параллелизм честно ограничен сверху: `exchange.settlement.parallelism` задаёт
максимум одновременных транзакций, по умолчанию 16. Без границы широкая пачка `PENDING` на разных
счетах открыла бы столько соединений, сколько операций, и исчерпала пул PostgreSQL.

Параллелизм не может превышать пул соединений: задачи расчёта держат соединение, пока ждут
блокировку периода, и при `parallelism ≥ maximum-pool-size` пул уходил бы в ожидание блокировки,
а страдали бы приём операций и чтение лимитов. Поэтому контекст не поднимается с такой
конфигурацией: `SettlementPoolGuard` требует `parallelism + 4 ≤ maximum-pool-size` и объясняет, что
менять, — проверяется фактический размер пула у Hikari, а не значение из YAML. Дефолты (16 при пуле
20) инвариант соблюдают.

Смена лимита идёт через тот же пул: `POST /limits` не открывает соединение на потоке запроса, а
ставит транзакционную работу (`LimitChangeApplier`) в очередь расчёта и ждёт её результата. Пока
идёт пересчёт флагов периода, соединение занято и ждёт блокировки, и на потоке запроса число таких
ожиданий ничем не ограничено — волна смен лимита выедала бы пул целиком, и первыми от этого
переставали работать приём операций и чтение лимитов. Пересчёт при этом остался в той же
транзакции, что и запись лимита: разносить их значило бы показать клиенту промежуточное состояние
«новый лимит — старые флаги», а при сбое пересчёта лимит остался бы записанным навсегда.

Проверено тестом `ParallelSettlementIntegrationTest`:

| Проверка | Что подтверждает |
| --- | --- |
| 6 валют в одной пачке | пик одновременных запросов к провайдеру выше 1, то есть курсы берутся параллельно |
| 8 операций одной пары «валюта + дата» | ровно **один** запрос к провайдеру вместо восьми |
| те же операции на разных датах | два запроса: вчерашний курс не подставляется на сегодняшнюю операцию |
| провайдер падает на одной валюте | остальные валюты пачки всё равно рассчитаны, сломанная осталась `PENDING` |
| 6 операций EUR и GBP одного месяца | сумма и кумулятивные флаги совпадают с расчётом по всем операциям |

Отдельно проверено, что тест на параллельность не проходит вхолостую: при возврате последовательного
однопоточного расчёта он падает с пиком, равным 1.

## SQL п.6: JOIN с подзапросом и агрегирующей функцией

`LimitAnalyticsQueryRepository` содержит два нативных запроса:

- `findExceeded` — `LEFT JOIN` с коррелированным подзапросом, выбирающим последний лимит не позже
  даты операции, плюс оконная `SUM(...) OVER (PARTITION BY ...)` для накопленной суммы. Лимит по
  умолчанию подставляется через `COALESCE`, потому что физически он не хранится. Раздел окна
  включает календарный месяц: сумма копится независимо в каждом месяце, как и флаг, который
  приложение считает по месяцам.
- `findLimitsWithSpentAmount` — `JOIN` с подзапросом, `GROUP BY` и `SUM` для остатка по лимитам.
  Вторая ветка `UNION ALL` добавляет дефолтный лимит для счёта с расходом в месяце, но без
  установленного лимита этой пары.
- Отдельный запрос `findLatestNotAfter` (JPQL) живёт в репозитории курсов и возвращает последний
  известный курс не позже даты операции вместе с датой записи: по ней `ExchangeRateService` решает,
  годится ли курс в резерв (см. ниже), а не берёт возраст из своей конфигурации.
- Нативный `upsert` для `exchange_rate` — `INSERT ... ON CONFLICT DO UPDATE SET close_rate =
  COALESCE(...)`. Обычный `save()` здесь упал бы на конфликте: две параллельные задачи дорасчёта
  умеют записать один и тот же курс, и это нормальный поток, а не ошибка. `COALESCE` в `SET`
  не даёт повторной записи с неполной строкой затереть уже известное `previous_close`.

Запросы проверяются на настоящем PostgreSQL: оконные функции, `date_trunc` и CHECK-ограничения
работают иначе, чем в H2, поэтому `ExceededTransactionsQueryIntegrationTest` не заменяет СУБД.

## База данных

Схема описана в Liquibase (schema first), `ddl-auto=validate`: миграции
`src/main/resources/db/changelog/`.

| Таблица | Назначение |
| --- | --- |
| `expense_transaction` | операции, применённый курс, сумма в USD, флаг `limit_exceeded` |
| `expense_limit` | установленные лимиты; неизменяемые |
| `exchange_rate` | собственный кэш дневных курсов (`close` и `previous_close`) |
| `spend_period_lock` | строки-замки для пессимистичной блокировки периода |

Категория расхода хранится кодом (`product`/`service`) — это совпадает с CHECK-ограничением
схемы и с тем, что пишет JPA-конвертер. Лимит не обновляется, но новые лимиты того же месяца
накапливаются в истории, поэтому запрет касается не истории, а момента: пара «счёт + категория +
момент установки» уникальна (`uc_expense_limit_instant`). Причина — SQL п.6 находит действующий
лимит джойном по значению `limit_datetime`, и без ограничения одна превышенная транзакция вернулась
бы двумя строками с разными суммами. Дата установки приводится к микросекундам — точности
`TIMESTAMPTZ`: два запроса с наносекундной разницей иначе выглядели бы для БД одним моментом, и
второй получил бы 409 без `reason`. Повторная установка на занятый момент отвечает `409`
(`reason=limit_already_set`), а не 422: сумма осмысленна, конфликтует уже сохранённая запись.

## Docker и CI

`Dockerfile` — multi-stage: слой сборки отделяет скачивание зависимостей от компиляции, в рантайм
копируется только JRE и jar, контейнер работает от непривилегированного пользователя.
`docker-compose.yml` поднимает сервис вместе с PostgreSQL и ждёт её готовности через healthcheck.
`.github/workflows/ci.yml` собирает и прогоняет `./mvnw verify` на GitHub Actions; ключ внешнего
API для этого не нужен — провайдер замокан.

## Оценка трудоёмкости

Оценка задания на старте — 6 рабочих дней при моей скорости. Фактически ушло больше, и основная
причина не в объёме кода (5642 строки production-кода и 5238 строк тестов вместе с комментариями
и пустыми строками; 183 тестов, из них 121 интеграционных). Время ушло на согласование семантики
расчёта с формулировками ТЗ: остаток считается от расходов всего месяца, а флаг — нарастающим
итогом до и включая текущую операцию. Эти два правила выглядят одинаково, но дают разные числа
в одной и той же строке таблицы, и больше всего проверок стоило именно на этом стыке.

| `SettlementCostIntegrationTest` | накопленная сумма из SQL совпадает с эталоном в Java; пачка из 400 операций одного периода рассчитывается за секунды, а не за десятки |
| `SettlementKickIntegrationTest` | проход дорасчётки по событию приёма: флаг появляется без ожидания планового прохода, пачка приёмов считается целиком и не плодит платные запросы |
| `ExpenseApiIntegrationTest` | REST-контракт сквозь реальный HTTP-порт, повторный `POST` с тем же `id` |
| `ApiErrorContractIntegrationTest` | коды и `application/problem+json` для ошибок формата и протокола: 400, 404, 405, 415, неизвестное поле в теле |
| `BoundedVirtualThreadExecutorTest` | ограничитель числа одновременных задач |
| `SettlementPoolGuardTest` | параллелизм расчёта против размера пула соединений |
| `ConfigurationDefaultsTest` | значения по умолчанию в records совпадают с `application.yaml`: иначе настройка в yaml выглядела бы действующей, а на деле не читалась бы |
| `SpecCaseOneEndToEndTest` | требование 6 ТЗ: «1 случай» таблицы целиком через HTTP — лимиты, операции и список превышений |

`SettlementKickIntegrationTest` поднимает **второй** контекст приложения: в основном тестовом
профиле фоновая дорасчётка выключена (`exchange.settlement.processing-enabled=false`) ради
детерминизма, поэтому считать транзакцию там некому. В этом классе обработка включена, а
`retry-delay=1h` — иначе рассчитать транзакцию мог бы планировщик, и проверка «досчёт по событию
приёма» ничего бы не доказывала. Контекст второй, поэтому прогон дороже примерно на минуту.

`AbstractIntegrationTest` поднимает один PostgreSQL в Testcontainers и WireMock на весь прогон
вручную, а не через `@Container`. Расширение Testcontainers останавливает контейнер после каждого
класса, а Spring переиспользует кэшированный контекст: следующий класс падал бы с «Connection
refused» при вполне рабочей схеме. Один контейнер на прогон с неизменным портом, наоборот, даёт
переиспользование контекста и заметно ускоряет прогон.

## AI в проекте

Инструментов было два, и разделение видно по тому, что за что отвечало:

| Инструмент | Что делал |
| --- | --- |
| JetBrains AI Assistant | Ранние итерации: каркас проекта, схема БД, первая версия интеграционных тестов, черновики DTO |
| opencode | Основная работа: досчёт по событию приёма, ручной досчёт `FAILED`, устранение квадратичности в расчёте флагов, MCP, полный аудит по ТЗ, рефакторинг и документация |

Каждая правка проверялась компиляцией и `./mvnw test`; ни одно утверждение из этого раздела не
принималось на веру: конфиги MCP проверялись настоящим MCP-клиентом, а расчёт флагов —
сверкой с пооперационным эталоном.

Где AI помог:

- **Каркас тестовой среды.** Скелет `AbstractIntegrationTest` (Testcontainers, WireMock, управляемый
  `Clock`) был собран быстро, но сразу дал неверную аннотацию `@Container` — это выяснилось только
  на полном прогоне: контейнер останавливался между классами, Spring держал в кэше контекст со
  старым портом, и десять тестов падали с «Connection refused». Нашёл это разбор полного лога,
  а не чтением кода: симптом указывал на сеть, а причина была в жизненном цикле контейнера.
- **Поиск ошибок в SQL и расчётах.** Именно интеграционные тесты на настоящем PostgreSQL поймали
  две ошибки, которые юнит-тесты принципиально не видели: оконная сумма в `findExceeded` не была
  разделена по месяцам, а сохранённые флаги не пересчитывались при поздней операции с ранней
  датой. Обе нашлись при сверке ожиданий с реальными данными.
- **Расчёт по плану ТЗ.** Пункты 1–6 разобраны и сверены с кодом: таблица соответствия с указанием
  конкретных классов и методов нашла то, чего не видно при чтении «сверху» — мёртвый код, два
  определения одной настройки, настройку, которую никто не читает, и расхождение между
  `application.yaml` и record-конфигурациями.

Что написано вручную:

- Семантика лимитов и разбор ТЗ: решения (кумулятивный флаг, остаток от начала месяца, UTC,
  пересчёт флагов при поздней операции) приняты вручную, потому что это предметная область, а не
  синтаксис. Каждое решение закреплено тестом и описано здесь.
- Стратегия отказоустойчивости и выбор границ API между `400` и `422`.
- Выбор часового пояса и его обоснование.

Где AI ошибался и как это заметили:

- **MCP-конфиги не работали вообще, хотя выглядели безобидно.** Три файла передавали `PGHOST`,
  `PGUSER` и `PGPASSWORD` через `env`, а сервер `@modelcontextprotocol/server-postgres` ждёт
  подключение **URL аргументом командной строки** и без него печатает `Please provide a database URL
  as a command-line argument`. Плюс подстановки синтаксиса у инструментов разные: Cursor понимает
  только `${env:VAR}`, Codex не подставляет значения в `args` и `env` вовсе. Заметил не чтением JSON,
  а настоящим MCP-клиентом: `initialize` + `tools/call` с `SELECT` от имени `exchange_readonly`.
- **API-ключ попал в репозиторий как значение по умолчанию** (`${RATES_API_KEY:<значение>}`).
  Последствия были не только в секрете: `@NotBlank` не мог сработать, сервис поднимался без
  переменной окружения и молча ходил в платное API по чужому ключу, а README утверждал обратное.
  Заметил сверкой README с кодом и `grep` по отслеживаемым файлам, а не при работе сервиса.
- **Первая версия досчёта по событию приёма теряла транзакции.** Если запрос прохода приходил, пока
  проход уже шёл, он просто отменялся — операция ждала планового, то есть `retry-delay`. В тесте с
  `retry-delay=1h` это был час ожидания, burst-тест падал по таймауту. Заметил по таймауту теста,
  а причину подтвердил `jstack`.
- **Первый вариант теста на этот же сценарий зациклил сам себя:** мок вызывал `pass()` на каждом
  круге, и цикл проходов не заканчивался. Поймал `jstack` зависшего surefire — 100% CPU в
  `Mockito` вместо стека проекта.
- **Ошибся в выборе кода ответа для «третьего знака после точки»:** предложил `422`, хотя `@Digits` на
  DTO уже отсекает это как ошибку формата. Заметил по падению теста (ожидался `422`, пришёл `400`) и
  тем, что в сервисе осталась недостижимая ветка. Проверка одного правила в двух местах — запах,
  а не решение.
- **Сгенерировал `PersistenceMapper` на MapStruct для преобразования сущностей в домен, но
  отказался доводить:** сущности не имеют сеттеров, а конструкторы требуют `@Inject`, которого нет в
  MapStruct 1.6.3. Заставить генератор работать ценой `@Setter` на доменных сущностях означало бы
  сломать инкапсуляцию ради экономии на пяти строках преобразования. Вертикаль откатил, преобразования
  оставил явными — они читаются и проверяются компилятором.
- **Не заметил проблему жизненного цикла контейнера в тестах:** сгенерированный код выглядел
  корректно, пока не отработал полный прогон.

Общий вывод: все три «тихие» ошибки (MCP, ключ, потерянная транзакция) не были видны ни в коде, ни в
тестах, пока не появился способ проверить утверждение настоящим инструментом — рукопожатием MCP,
`grep` по отслеживаемым файлам, таймаутом теста. Проверяемость дороже скорости генерации.

### Скиллы

В `.agents/skills/` три скилла в формате открытого стандарта Agent Skills (YAML-заголовок с `name`
и `description`), одинаково читаются Codex, Cursor, Claude Code и Copilot:

| Скилл | Когда применяется |
| --- | --- |
| `limit-testing` | тесты расчёта лимитов, разбор сценариев ТЗ, граничные случаи |
| `rate-provider` | подключение нового внешнего API курсов, таймауты, повторы, отказы |
| `db-migration` | изменение схемы, новые колонки, индексы, ограничения |

Спецсимлинк для Claude Code: `.claude/skills` → `.agents/skills`, как советует приложение к ТЗ.

**Как применить скилл.** Он подбирается агентом сам по полю `description` в YAML-заголовке, поэтому
надёжнее назвать его в запросе:

> Примени скилл `limit-testing`: добавь интеграционный тест на позднюю операцию с ранней датой.

В opencode есть явный инструмент `skill` — `skill(name="limit-testing")` читает `SKILL.md` и
подставляет инструкцию в контекст вместе с путём к файлам скилла. В Claude Code, Cursor и Copilot
достаточно упомянуть скилл в тексте запроса; каталоги поиска для них заданы выше.

Проверено на практике, а не «должно работать»: скилл находится и читается, команды из него
(`./mvnw -Dtest=LimitCalculatorTest test`) выполняются, а ссылки на классы в нём соответствуют
репозиторию.

**Ловушка, о которой стоит знать.** Скилл читается один раз за сессию агента. После правки
`SKILL.md` в уже открытой сессии агент продолжает работать со старой версией — при проверке правки
`limit-testing` (убрано упоминание несуществующего Awaitility) файл на диске уже был новым, а
в подгрузке остался старый текст. Правя скилл, перечитай его или начни новую сессию, иначе
инструкция, которую агент видит, не совпадёт с репозиторием.

### MCP

Подключены два сервера, конфигурация лежит в репозитории: `.mcp.json` (Claude Code),
`.cursor/mcp.json` и `.codex/config.toml` — протокол MCP единый, различается только файл и способ
чтения пароля.

MCP-сервер подключается не от пользователя сервиса, а от `exchange_readonly` с правами только на
чтение: агент может смотреть схему и данные, но не может их изменить — `INSERT` в `expense_limit`
отклоняется PostgreSQL с `permission denied`. Пользователя создаёт
`ops/postgres-init/01-readonly-user.sh` при первом запуске `docker compose up` на пустом томе, пароль
приходит из `EXCHANGE_READONLY_PASSWORD`. Скрипт выполняется один раз, поэтому после
`docker compose down -v` том пуст и пользователя нужно создать заново, задав
`EXCHANGE_READONLY_PASSWORD` (и то же значение в `PGPASSWORD`).

**Что нужно, чтобы сервер подключился.** Локальная БД из `docker compose` доступна на порту `5433`.
Пароль лежит в `.env` и в репозиторий не попадает, поэтому перед запуском инструмента переменные
нужно экспортировать в сессию:

```bash
set -a && source .env && set +a
```

Пароль попадает в URL подключения, а URL передаётся **аргументом командной строки**: сервер
`@modelcontextprotocol/server-postgres` не читает `PGHOST`/`PGUSER`/`PGPASSWORD` из окружения и без
URL завершается с `Please provide a database URL as a command-line argument`. Поэтому три конфига
читают пароль по-разному — это особенности инструментов, а не стилистика:

| Инструмент | Файл | Как собирается URL |
| --- | --- | --- |
| Claude Code | `.mcp.json` | `${PGPASSWORD}` подставляется в `args` из окружения процесса |
| Cursor | `.cursor/mcp.json` | `${env:PGPASSWORD}` — синтаксис подстановки Cursor (он не понимает `${VAR:-default}`) |
| Codex | `.codex/config.toml` | `sh -c` собирает URL из переменных, которые Codex пересылает по имени через `env_vars`: подстановки `${VAR}` в `args` он не делает |

Пароль попадает в URL, поэтому в `PGPASSWORD` годится только значение, безопасное для URL: без
`@`, `:`, `/`, `?` и `#` (в `.env` для локального запуска — `readonly-local`).

Проверяется без агента — обычным `psql` внутри контейнера:

```bash
docker compose exec -e PGPASSWORD=readonly-local -T postgres \
  psql -h 127.0.0.1 -U exchange_readonly -d exchange -c "SELECT count(*) FROM expense_transaction;"
```

| Сервер | Зачем |
| --- | --- |
| PostgreSQL | агент видит реальную схему и данные, может сверить запрос с данными |
| Context7 | актуальная документация по Spring Boot 4 и Jackson 3 |

Где сервер полезен: расследование ошибок в SQL. Момент разбиения суммы по месяцам в `findExceeded`
найден интеграционным тестом на настоящем PostgreSQL, а `SELECT` к этой БД через MCP сразу
показывает, что февральская операция наследует январский итог, — то есть раздел окна не содержит
месяца. Поиск по коду давал бы три кандидата, запрос к данным — сразу конкретную причину.

Инструкции для агентов лежат в `AGENTS.md`: архитектура, команды, конвенции и перечень того, чего
делать нельзя.
