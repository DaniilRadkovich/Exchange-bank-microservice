# exchangeservice

Микросервис контроля месячных лимитов расходов в банке: принимает расходные операции в валюте
счёта, переводит их в USD по биржевому курсу закрытия и помечает операции, превысившие месячный
лимит. Лимиты ведутся раздельно для категорий `product` и `service`.

Реализация тестового задания
`Тестовое_задание_Junior_Java_разработчика_2026.pdf` (пункты 1–6 обязательные, частично 1\*, 3\*,
5\*).

## Стек

Java 21, Spring Boot 4.1.1, Spring Web MVC на виртуальных потоках, Spring Data JPA, Liquibase
(schema first), PostgreSQL 17, RestClient, springdoc (OpenAPI), Testcontainers, WireMock,
REST Assured, JUnit 5, AssertJ, Lombok, logback + logstash-logback-encoder.

## Запуск

Нужен Docker (для тестов) и JDK 21. Сервис вместе с БД поднимается одной командой:

```bash
RATES_API_KEY=<ключ> docker compose up --build
```

Либо вручную, если БД уже есть: Схема создаётся Liquibase при старте, отдельная ручная
подготовка БД не нужна.

```bash
# PostgreSQL для ручного запуска сервиса
docker run -d --name exchange-db -p 5432:5432 \
  -e POSTGRES_DB=exchange -e POSTGRES_USER=exchange -e POSTGRES_PASSWORD=exchange \
  postgres:17-alpine

./mvnw spring-boot:run -Dspring-boot.run.profiles=dev
```

Swagger UI: <http://localhost:8080/swagger-ui.html>, OpenAPI: `/v3/api-docs`,
health-check: `/actuator/health`.

Тесты (нужен только установленный Docker, внешний API курсов мокается WireMock):

```bash
./mvnw test        # 70 тестов: unit + интеграционные
./mvnw verify      # то же + проверки сборки
```

Конфигурация задаётся переменными окружения: `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`,
`DB_POOL_SIZE`, `RATES_API_BASE_URL`, `RATES_API_KEY`. Профили `dev`, `test`, `prod`
(см. `src/main/resources/application*.yaml`).

## Часовой пояс границ месяца: UTC

Месячные границы считаются в **UTC**, это задаётся свойством `exchange.limit.timezone`.
Следовательно, операция 2022-01-31T23:30:00+06:00 попадает в январь, потому что по UTC это
2022-01-31T17:30Z. Значение вынесено в конфигурацию, а не зашито в код: при смене зоны меняется
один параметр, а вся логика остаётся прежней.

## Семантика лимитов

Ключевые решения, которые неочевидны из ТЗ и зафиксированы тестами:

- **Флаг кумулятивный.** `limit_exceeded` сравнивает накопленную сумму всех операций месяца «до и
  включая текущую» с лимитом, действовавшим на момент её совершения. Строгое сравнение: при
  остатке ровно 0 флаг равен `false`.
- **Лимит принадлежит паре «счёт + категория + месяц».** Операции соседнего месяца или соседней
  категории не влияют на флаг.
- **Смена лимита внутри месяца не меняет флаги более ранних операций** — они рассчитаны по лимиту,
  действовавшему тогда (п.4 ТЗ).
- **Остаток, в отличие от флага, считается от расходов всего месяца с 1-го числа**, а не от даты
  установки лимита. Это даёт остаток 900 в ТЗ: лимит 2000 USD от 10.01, расходы 500 + 600.
- **Лимит по умолчанию физически не хранится.** 1000 USD с датой в начале месяца вычисляются на
  лету, поэтому у такого лимита `id == null`.
- **Поздняя операция с ранней датой пересчитывает флаги.** Операция, дошедшая до расчёта позже
  операций с поздними датами, увеличивает накопленный итог и для них. Без пересчёта сохранённые
  флаги остались бы навсегда заниженными, и клиент получил бы неверный отчёт.

## API

Два контура API разведены по URL.

Интеграция с банковскими сервисами:

| Метод | Путь | Ответ |
| --- | --- | --- |
| `POST` | `/api/v1/transactions` | `202 Accepted`, тело — транзакция в статусе `PENDING` |
| `GET` | `/api/v1/transactions/{id}` | состояние расчёта: курс, сумма в USD, флаг |

Клиентский API:

| Метод | Путь | Ответ |
| --- | --- | --- |
| `POST` | `/api/v1/limits` | `201 Created`, установленный лимит |
| `GET` | `/api/v1/limits` | лимиты с остатком, новые первыми |
| `GET` | `/api/v1/limits/exceeded` | превышенные транзакции с параметрами превышенного лимита |

Дата установки лимита клиентом не передаётся: её проставляет сервис из бина `java.time.Clock`,
поэтому лимит нельзя «отмотать» в прошлое или в будущее. Обновление существующего лимита
запрещено (п.5 ТЗ) — новый лимит создаётся новым запросом.

Ошибки — единый формат ProblemDetail (RFC 9457), `application/problem+json`:

| Код | Когда |
| --- | --- |
| `400` | Bean Validation и нечитаемый JSON: поле, причина, перечень нарушений |
| `404` | неизвестная транзакция или лимит |
| `422` | формат верен, но значение смыслово неприемлемо, например `reason=unknown_currency` |
| `500` | непредвиденная ошибка, детали не раскрываются |

Точность суммы (`@Digits`) проверяется на границе API как ошибка формата (`400`), а не в сервисе
второй раз: одна проверка одного правила.

## Стратегия работы с внешним API курсов

Внешний провайдер — [Twelve Data](https://twelvedata.com), дневной интервал (`1day`), берётся
`close`, а при отсутствии торгов — `previous_close` (п.3 ТЗ).

Запрос к внешнему API платный и медленный, поэтому курсы хранятся в собственной БД
(`exchange_rate`) и используются преимущественно: `ExchangeRateService` сначала смотрит кэш и
только потом обращается к провайдеру. Повторный запрос за ту же пару и дату не выполняется.

**Приём транзакций не зависит от доступности провайдера.** Это ключевое требование ТЗ:

1. `POST /api/v1/transactions` сохраняет транзакцию в статусе `PENDING` и сразу отвечает `202`.
   Внешний API в этом потоке не вызывается.
2. Расчёт курса и флага выполняется отдельно (`PendingSettlementScheduler`, виртуальные потоки).
3. Клиент читает состояние расчёта через `GET /api/v1/transactions/{id}`.
4. Если провайдер недоступен, транзакция остаётся `PENDING` и дорасчитывается позже, пока не
   исчерпает `exchange.settlement.max-attempts`.

Таймауты и повторы заданы явно (`exchange.rates.*`): `connect-timeout` и `read-timeout` не дают
висеть на мёртвом провайдере, а ограниченное число повторов с экспоненциальной задержкой
(`RetryingCaller`) переживает кратковременные сбои, не превращаясь в лавину повторов при
недоступности.

## Наблюдаемость

Actuator отдаёт `/actuator/health` (с деталями при авторизации) и `/actuator/prometheus`.

Метрики Micrometer по работе с внешним API курсов — главный эксплуатационный сигнал, потому что
именно там платные и медленные запросы:

| Метрика | Смысл |
| --- | --- |
| `exchange.rates.provider.duration` | длительность вызовов внешнего API вместе с повторами |
| `exchange.rates.provider.requests{outcome=miss\|failure}` | сколько раз пошли в провайдер и чем закончилось |
| `exchange.rates.cache.lookups{outcome=hit\|miss\|unresolved}` | попадания и промахи собственной БД |

Рост доли `outcome=unresolved` означает, что транзакции копятся в `PENDING`; рост `miss` при
нормальном `hit` означает поток операций по датам, которых ещё нет в кэше.

## Многопоточность

Транзакции одного клиента приходят параллельно, и два запроса не должны «увидеть» один и тот же
остаток лимита (п.4 ТЗ).

Расчёт выполняется в транзакции БД и начинается с пессимистичной блокировки периода:
`SELECT ... FOR UPDATE` на строке-замке `spend_period_lock` для пары «счёт + категория + месяц».
Блокировка берётся **до** чтения накопленной суммы, поэтому второй поток ждёт и считает уже
обновлённые расходы. Строка-замок создаётся лениво при первом расчёте периода.

Проверено тестом `ConcurrentSettlementIntegrationTest`: 30 операций в 6 потоках дают сумму ровно
3000 USD и флаги, совпадающие с кумулятивным пересчётом по всем операциям.

## SQL п.6: JOIN с подзапросом и агрегирующей функцией

`LimitAnalyticsQueryRepository` содержит три нативных запроса:

- `findExceeded` — `LEFT JOIN` с коррелированным подзапросом, выбирающим последний лимит не позже
  даты операции, плюс оконная `SUM(...) OVER (PARTITION BY ...)` для накопленной суммы. Лимит по
  умолчанию подставляется через `COALESCE`, потому что физически он не хранится. Раздел окна
  включает календарный месяц: сумма копится независимо в каждом месяце, как и флаг, который
  приложение считает по месяцам.
- `findLimitsWithSpentAmount` — `JOIN` с подзапросом, `GROUP BY` и `SUM` для остатка по лимитам.
- `findLatestNotAfter` — последний известный курс не позже даты операции.

Запросы проверяются на настоящем PostgreSQL: оконные функции, `date_trunc` и CHECK-ограничения
работают иначе, чем в H2, поэтому `ExceededTransactionsQueryIntegrationTest` не заменяет СУБД.

## База данных

Схема описана в Liquibase (schema first), `ddl-auto=validate`: миграции
`src/main/resources/db/changelog/`.

| Таблица | Назначение |
| --- | --- |
| `expense_transaction` | операции, применённый курс, сумма в USD, флаг `limit_exceeded` |
| `expense_limit` | установленные лимиты; неизменяемые |
| `exchange_rate` | собственный кэш дневных курсов (`close` и `previous_close`) |
| `spend_period_lock` | строки-замки для пессимистичной блокировки периода |

Категория расхода хранится кодом (`product`/`service`) — это совпадает с CHECK-ограничением
схемы и с тем, что пишет JPA-конвертер. Лимит не обновляется, но новые лимиты накопились бы в
истории, поэтому `limit_datetime` не уникален: уникальность обеспечена на уровне домена
(запрет обновления), а не жёстким ограничением, которое ломало бы чтение истории.

## Docker и CI

`Dockerfile` — multi-stage: слой сборки отделяет скачивание зависимостей от компиляции, в рантайм
копируется только JRE и jar, контейнер работает от непривилегированного пользователя.
`docker-compose.yml` поднимает сервис вместе с PostgreSQL и ждёт её готовности через healthcheck.
`.github/workflows/ci.yml` собирает и прогоняет `./mvnw verify` на GitHub Actions; ключ внешнего
API для этого не нужен — провайдер замокан.

## Оценка трудоёмкости

Оценка задания на старте — 6 рабочих дней при моей скорости. Фактически ушло больше, и основная
причина не в объёме кода: 3610 строк production-кода и 1765 строк тестов, 70 тестов, из них 48
интеграционных. Время ушло на согласование семантики расчёта с формулировками ТЗ: остаток
считается от расходов всего месяца, а флаг — нарастающим итогом до и включая текущую операцию.
Эти два правила выглядят одинаково, но дают разные числа в одной и той же строке таблицы, и
больше всего проверок стоило именно на этом стыке.

| `ConcurrentSettlementIntegrationTest` | конкурентный расчёт в 6 потоках |
| `ExpenseApiIntegrationTest` | REST-контракт сквозь реальный HTTP-порт |
| `SpecCaseOneEndToEndTest` | требование 6 ТЗ: «1 случай» таблицы целиком через HTTP — лимиты, операции и список превышений |

`AbstractIntegrationTest` поднимает один PostgreSQL в Testcontainers и WireMock на весь прогон

refused» при вполне рабочей схеме. Один контейнер на прогон с неизменным портом, наоборот, даёт
переиспользование контекста и заметно ускоряет прогон.

## AI в проекте

Инструмент: JetBrains AI Assistant (интерактивный режим opencode поверх Claude) для черновых
правок, рефакторинга и комментариев; каждая правка проверялась компиляцией и тестами.

Где AI помог:

- **Каркас тестовой среды.** Скелет `AbstractIntegrationTest` (Testcontainers, WireMock, управляемый
  `Clock`) был собран быстро, но сразу дал неверную аннотацию `@Container` — это выяснилось только
  на полном прогоне: контейнер останавливался между классами, Spring держал в кэше контекст со
  старым портом, и десять тестов падали с «Connection refused». Нашёл это разбор полного лога,
  а не чтением кода: симптом указывал на сеть, а причина была в жизненном цикле контейнера.
- **Поиск ошибок в SQL и расчётах.** Именно интеграционные тесты на настоящем PostgreSQL поймали
  две ошибки, которые юнит-тесты принципиально не видели: оконная сумма в `findExceeded` не была
  разделена по месяцам, а сохранённые флаги не пересчитывались при поздней операции с ранней
  датой. Обе нашлись при сверке ожиданий с реальными данными.

Что написано вручную:

- Семантика лимитов и разбор ТЗ: решения (кумулятивный флаг, остаток от начала месяца, UTC,
  пересчёт флагов при поздней операции) приняты вручную, потому что это предметная область, а не
  синтаксис. Каждое решение закреплено тестом и описано здесь.
- Стратегия отказоустойчивости и выбор границ API между `400` и `422`.
- Выбор часового пояса и его обоснование.

Где AI ошибался и как это заметили:

- Ошибся в выборе кода ответа для «третьего знака после точки»: предложил `422`, хотя
  `@Digits` на DTO уже отсекает это как ошибку формата. Заметил по падению теста (ожидался `422`,
  пришёл `400`) и тем, что в сервисе осталась недостижимая ветка. Проверка одного правила в двух
  местах — запах, а не решение.
- Сгенерировал `PersistenceMapper` на MapStruct для преобразования сущностей в домен, но
  отказался доводить: сущности не имеют сеттеров, а конструкторы требуют `@Inject`, которого нет в
  MapStruct 1.6.3. Заставить генератор работать ценой `@Setter` на доменных сущностях означало бы
  сломать инкапсуляцию ради экономии на пяти строках преобразования. Вертикаль откатил, преобразования
  оставил явными — они читаются и проверяются компилятором.
- Не заметил проблему жизненного цикла контейнера в тестах: сгенерированный код выглядел
  корректно, пока не отработал полный прогон.

### MCP

Подключены два сервера, конфигурация лежит в репозитории: `.mcp.json` (Claude Code), `.cursor/mcp.json`
и `.codex/config.toml` — протокол MCP единый, различается только файл. Секреты не закоммичены:
значения берутся из переменных окружения.

MCP-сервер подключается не от пользователя сервиса, а от `exchange_readonly` с правами только на
чтение: агент может смотреть схему и данные, но не может их изменить. Пользователя создаёт
`ops/postgres-init/01-readonly-user.sh` при первом запуске `docker compose up`, пароль приходит из
`EXCHANGE_READONLY_PASSWORD`. Скрипт выполняется один раз на пустом томе, поэтому после удаления
тома `docker compose down -v` его нужно задать заново — иначе compose не поднимется.

| Сервер | Зачем |
| --- | --- |
| PostgreSQL | агент видит реальную схему и данные, может сверить запрос с данными |
| Context7 | актуальная документация по Spring Boot 4 и Jackson 3 |

Где сервер полезен: расследование ошибок в SQL. Момент разбиения суммы по месяцам в `findExceeded`
найден интеграционным тестом на настоящем PostgreSQL, а `SELECT` к этой БД через MCP сразу
показывает, что февральская операция наследует январский итог, — то есть раздел окна не содержит
месяца. Поиск по коду давал бы три кандидата, запрос к данным — сразу конкретную причину.

Инструкции для агентов лежат в `AGENTS.md`: архитектура, команды, конвенции и перечень того, чего
делать нельзя.
