# Миграции БД (Liquibase, schema first)

## Правило, которое определяет всё остальное

Схема — источник истины, сущности только отображаются на неё. В `application.yaml` стоит
`ddl-auto: validate`, поэтому Hibernate не создаёт и не меняет ничего: расхождение схемы и
сущности валит старт приложения.

Отсюда порядок любой правки: **сначала миграция, потом сущность.** Если сделать наоборот, то на
следующем запуске `validate` упадёт, а при `ddl-auto: update` тихо создалась бы расходящаяся схема.

## Расположение и именование

- Каталог: `src/main/resources/db/changelog/`
- Нумерация по порядку применения: `001-create-schema.sql`, `002-unique-limit-instant.sql`,
  `003-rate-precision.sql`, `004-amount-usd-precision.sql`. Следующий номер — 005.
- Формат — `--liquibase formatted sql`, как в существующем `001-create-schema.sql`.
- Файл подключается в `db/changelog.xml`: Liquibase не подхватывает файлы из каталога сам. Новый
  файл без `<include>` просто не применится, и об этом узнаёшь по падению `validate`.

```sql
--liquibase formatted sql

--changeset exchange:002-settlement-index
-- Индекс под findResolvedInPeriod: выборка периода всегда идёт по счёту, категории и времени.
CREATE INDEX ix_expense_transaction_period
  ON expense_transaction (account_from, expense_category, occurred_at);
```

Идентификатор `--changeset` должен быть уникален навсегда: Liquibase определяет «уже применён»
именно по нему и по чексумме файла. Правка применённого changeset приведёт к ошибке валидации
чексуммы, и уже развёрнутая БД не восстановится сама — новую правку оформляй новым
`--changeset`.

## Что должно быть в схеме

Сейчас в `001-create-schema.sql` описаны:

| Таблица | Ключевые ограничения |
| --- | --- |
| `expense_transaction` | `currency_code CHAR(3)`, `expense_category VARCHAR(16)`, CHECK на категорию |
| `expense_limit` | те же ограничения на категорию, `uc_expense_limit_instant` — один лимит на момент |
| `exchange_rate` | уникальность `(base_currency, quote_currency, rate_date)` |
| `spend_period_lock` | первичный ключ `(account_from, expense_category, budget_period)` |

Придерживайся существующих правил:

- **Категория хранится кодом в нижнем регистре** (`product`, `service`), а не `PRODUCT`. Это
  совпадает с CHECK-ограничением и с тем, что пишет `ExpenseCategoryConverter`. Схема и JPA должны
  говорить одно и то же, иначе запись в базу падает на ограничении.
- **Валюта — код ISO 4217** в `CHAR(3)`, не объект.
- **Время — `TIMESTAMPTZ`**. JDBC возвращает `Instant`, домен работает с `OffsetDateTime`; зону
  задаёт `hibernate.jdbc.time_zone: UTC` в `application.yaml` плюс адаптеры
  (`JpaLimitStore.toDomain`, `JpaTransactionStore.toDomain`), а не схема. Часовой пояс месячных
  границ — константа `BudgetPeriod.LIMIT_TIMEZONE`, он не настраивается.
- **Деньги — `NUMERIC(19, 2)` для сумм и `NUMERIC(19, 10)` для курсов.** `double` в БД означает
  расхождения в сравнении с лимитом, а `NUMERIC(19, 4)` для курса — потерю денег: курс KZT около
  0.0025 округляется с погрешностью до 2%, а курс мельче 0.00005 обнуляется и отвергается CHECK
  `close_rate > 0`, из-за чего валюта становится нерасчётной навсегда. Единственный источник
  значения — `ExchangeRate.RATE_SCALE`, в схеме ему соответствует `NUMERIC(19, 10)`.
  Исключение из правила — `expense_transaction.amount_usd`: это `amount × usd_rate`, произведение,
  а не сумма, поэтому колонка `NUMERIC(30, 2)`. При курсе выше единицы произведение выходит за 19
  знаков, и сужение колонки обратно сделает часть принятых по формату транзакций несохранимой:
  `sum` проверяет `@Digits(integer = 17)`, то есть формат, а не смысл. Ширины согласованы:
  `amount < 10^17`, `usd_rate < 10^9` (курс обязан пройти запись в `exchange_rate`), произведение
  `< 10^26`, а `NUMERIC(30, 2)` вмещает `< 10^28`.
- **Внешние ключи и индексы обязательны.** Индексы нужны на колонках, по которым идут выборки
  `findResolvedInPeriod`, `findLatestNotAfter` и запросы п.6 (`findExceededTransactions`,
  `findLimitsWithSpent`).
- **Запись курсов идёт нативным `INSERT ... ON CONFLICT DO UPDATE`**, а не через `save()`: две
  параллельные задачи дорасчёта умеют записать один и тот же курс, и наивный `save()` на этом
  конфликте упал бы. Если меняешь `ExchangeRateJpaRepository.upsert`, сохраняй `COALESCE` в `SET`:
  без него повторная запись с неполной строкой затрёт уже известное `previous_close`.

## После изменения схемы

```bash
# Проверить, что схема применилась и validate проходит
JAVA_HOME=$(/usr/libexec/java_home -v 21) ./mvnw test
```

Интеграционные тесты поднимают PostgreSQL в Testcontainers и прогоняют Liquibase с нуля, поэтому
ошибка в SQL ловится сразу. Юнит-тесты схему не трогают.

## Обратная совместимость

Сервис работает на уже развёрнутой БД. Поэтому:

- Не удаляй и не переименовывай колонку, которая читается запросом.
- Не меняй тип существующей колонки: переноси данные отдельной миграцией.
- Новую колонку делай `NULL`-допустимой либо с `DEFAULT`, иначе на большой таблице таблица
  переписывается целиком и блокирует запись.
- Удаление данных — только явная миграция с задокументированным основанием.

## Чего не делать

- Не ставь `ddl-auto: update` «чтобы заработало». Это маскирует расхождение, а в следующем
  развёртывании приведёт к несовпадению схемы с репозиторием.
- Не правь применённый `--changeset` вместо создания нового.
- Не храни в БД то, что выводится из остальных данных: лимит по умолчанию 1000 USD физически не
  сохраняется и подставляется через `COALESCE`. Новые вычисляемые величины тоже не должны
  попадать в таблицу.
- Не добавляй индекс «на всякий случай»: индексы стоят на записи, а лишние незаметно съедают
  время вставки транзакций. Добавляй под конкретный запрос и комментируй, какой именно он
  ускоряет.
