## Что это за проект

Микросервис контроля месячных лимитов расходов в банке. Принимает расходные операции в валюте
счёта, переводит их в USD по биржевому курсу закрытия, помечает операции, превысившие месячный
лимит. Лимит ведётся для пары «счёт + категория (`product`/`service`)», по умолчанию 1000 USD.
Границы месяца — **UTC**.

Спецификация: `Тестовое_задание_Junior_Java_разработчика_2026.pdf`. Подробности решений — в
`README.md`.

## Команды

Нужен JDK 21. На macOS `JAVA_HOME=$(/usr/libexec/java_home -v 21)`. Нужен Docker для тестов.

```bash
./mvnw test                                   # 172 теста, unit + интеграционные
./mvnw test -Dtest=LimitCalculatorTest         # один набор
./mvnw spring-boot:run -Dspring-boot.run.profiles=dev
```

Интеграционные тесты сами поднимают PostgreSQL в Testcontainers и WireMock. Вручную ничего
готовить не нужно, внешний API курсов не покупается.

## Архитектура

Пакеты в `com.idftech.exchangeservice`:

| Пакет | Что внутри | Правило |
| --- | --- | --- |
| `domain` | `ExpenseTransaction`, `ExpenseLimit`, `ExchangeRate`, `BudgetPeriod` | Чистый Java. Нет Spring, нет аннотаций, нет знания о БД. Сюда попадает вся логика расчёта. |
| `application` | сервисы, порты, исключения | Знает про домен и порты, не знает про HTTP и JPA. |
| `application/port` | интерфейсы хранилищ и провайдера | Реализации — в `infra`. |
| `application/config` | record-конфигурации расчёта и курсов | Читается и сервисами, и `infra`; в `infra` их держать нельзя — иначе `application` начнёт знать про инфраструктуру. |
| `infra/persistence` | JPA-сущности, адаптеры, нативные запросы | Единственное место со знанием о SQL. |
| `infra/rate` | HTTP-клиент внешнего API курсов | Единственное место со знанием о формате ответа провайдера. |
| `api` | контроллер, DTO, ProblemDetail | Только транспорт и валидация формы. |

Зависимости направлены внутрь: `api → application → domain`. `infra` реализует порты и подключается
через Spring. `domain` не знает ни о ком, поэтому тестируется без контейнера.

Направление зависимостей компилятор не проверяет: `application` спокойно импортирует `infra`, всё
собирается и все тесты зелёные. Поэтому граница проверяется тестом `LayeringTest` по исходникам:
`application` не знает про `infra`, `domain` не знает ни про Spring, ни про JPA, ни про прикладной
слой. Переносить настройки в `infra.config` ради того, чтобы их читал сервис, — ошибка: настройки
расчёта живут в `application.config`.

## Конвенции, которые нельзя нарушать

1. **Схема — источник истины.** `ddl-auto: validate` и в основном конфиге, и в тестовом
   (`application-test.yaml`). Новая колонка: сначала миграция в `db/changelog/`, потом поле в
   сущности. Никогда `update`. Типы должны совпадать буквально: `CHAR(3)` в схеме требует
   `columnDefinition = "bpchar(3)"` в `@Column`, иначе валидация падает на старте.
   Пара «счёт + категория + момент установки» уникальна (`uc_expense_limit_instant`), потому что SQL
   п.6 джойнит лимит по значению `limit_datetime`: два лимита на один момент вернули бы одну
   превышенную транзакцию двумя строками. Дата установки приводится к микросекундам — точности
   `TIMESTAMPTZ`, — иначе наносекундная разница двух запросов выглядела бы для БД одним моментом.
2. **Время только через `java.time.Clock`.** Никаких `LocalDate.now()` и `OffsetDateTime.now()` в
   прикладном коде: тесты не смогут «перевести часы». В базе время — `TIMESTAMPTZ`.
   Часовой пояс границ месяца — **константа `BudgetPeriod.LIMIT_TIMEZONE` (UTC)**, не настройка.
   Расчёт флага, команда изменения лимита и запросы остатка обязаны брать месяц из одного места;
   второй источник зоны в YAML разъехал бы с расчётом молча. Не возвращай
   `exchange.limit.timezone`.
3. **Деньги — `BigDecimal`.** Суммы со scale 2, курсы со scale **10** (`ExchangeRate.RATE_SCALE`,
   единственный источник значения; в схеме это `NUMERIC(19, 10)` для `close_rate`,
   `previous_close`, `usd_rate`). Четрёх знаков не хватает реальным курсам к USD: у тенге курс
   около 0.0025 (округление даёт до 2% погрешности), а курс мельче 0.00005 — VND, IDR, KRW —
   обнуляется вовсе и не проходит CHECK `close_rate > 0`, из-за чего валюта становится
   нерасчётной навсегда. Ширины тоже согласованы: `amount` и `limit_sum` — `NUMERIC(19, 2)`
   (17 знаков целых, столько же проверяет `@Digits`), а `amount_usd` — **`NUMERIC(30, 2)`**, потому
   что это произведение суммы на курс, а не сумма. При курсе выше единицы произведение выходит за 19
   знаков, и `numeric field overflow` делал принятую по формату транзакцию несохранимой; сузить
   колонку обратно нельзя, а отвергать такую сумму на приёме нельзя — это потеря данных. Регрессия:
   `ExchangeRateIntegrationTest#maximalSumIsConvertedWithoutOverflow`. Сравнение лимита строгое
   (`spent > limit`): остаток ровно 0 не считается превышением. Сбой записи курса в БД нельзя ловить вместе со сбоем внешнего API: иначе
   нарушение ограничения нашей схемы выглядит в логе как недоступность биржи, и сбой уходит в
   `FAILED` без видимой причины. Граница проходит по `ExchangeRateService`: пустой результат — виноват
   провайдер, исключение наружу — виноват сервис. Дальше эту границу стирать нельзя: `Optional` вместо
   `RateResolution` в `ParallelRateResolver` означал бы, что отказ задачи снова станет «курсом
   недоступен», а это ровно тот баг, который был — фикс жил в одиночном пути `settle`, а пакетный
   `settlePending`, то есть промышленный, маскировал сбой. Пробрасывать отказ из резолвера наружу тоже
   нельзя: одна сломанная транзакция встала бы перед всей пачкой. Регрессии:
   `ParallelRateResolverTest#serviceFailureIsNotReportedAsUnavailableRate` и
   `ExchangeRateIntegrationTest#cacheWriteFailureInBatchIsNotBlamedOnProvider`.
4. **Категория в БД — код в нижнем регистре** (`product`, `service`), не имя enum. Это совпадает с
   CHECK-ограничением схемы и с `ExpenseCategoryConverter`.
5. **`limit_exceeded` кумулятивный** по месяцу: сравнивается накопленная сумма «до и включая
   текущую» с лимитом, действовавшим на момент совершения операции. Не переписывай это на
   сравнение с остатком от даты установки лимита.
   Смена лимита пересчитывает флаги периода (`SettlementApplier.recalculatePeriod` из
   `LimitCommandService.createLimit`): новый лимит не применяется задним числом, но меняет порог
   для более поздних операций, включая уже посчитанные. Операция с будущей датой — единственный
   случай, где без пересчёта флаг остался бы устаревшим навсегда.
   Порядок транзакций с одинаковым временем обязан совпадать с PostgreSQL: флаг считает
   приложение, накопленную сумму отдаёт SQL. `UUID.compareTo` сравнивает полу-слова как знаковые
   `long`, а PostgreSQL — 16 байт беззнаково, поэтому tie-break реализован в `LimitCalculator`
   сравнением канонического текста UUID. Идентификаторы вида `00000000-…-00000000000N` в обоих
   порядках совпадают, поэтому расхождение не видно на тестовых UUID и проявляется на
   `UUID.randomUUID()`. Там же ограничение лимита месяцем операции: лимит прошлого месяца не
   подставляется к операции текущего.
   Пересчёт флагов периода — `LimitCalculator.computeFlags`: накопленный итог накапливается одним
   проходом по отсортированному списку. Не возвращай расчёт суммы «заново для каждой операции»
   (`spentUpTo` в цикле) — это квадратичный пересчёт на каждой транзакции, и он не заметен на
   тестовых трёх операциях таблицы ТЗ.
   Границы месяца обязаны соблюдаться и в `LimitAnalyticsQueryRepository.findLimitsWithSpentAmount`,
   где SQL и домен встречаются лицом к лицу: `JOIN` расхода и `NOT EXISTS` дефолтной строки
   ограничены `:periodStart`/`:periodEnd` начало включительно, конец исключительно, как
   `findLimitsInPeriod`. Без этой границы `GET /limits` присоединяет расход февраля к январскому
   лимиту и показывает остаток 3900 там, где `GET /limits/exceeded` честно пишет «превышен лимит
   1000» — два ответа об одном клиенте противоречат друг другу. Регрессия:
   `ExpenseApiIntegrationTest#previousMonthLimitDoesNotAbsorbCurrentMonthSpending`.
6. **Блокировку периода берёт расчёт, а не приём.** `SELECT ... FOR UPDATE` на строке-замке
   `spend_period_lock` берётся **до** чтения накопленной суммы, иначе параллельные потоки увидят
   один и тот же остаток. Транзакция расчёта живёт в `SettlementApplier`, а не в
   `TransactionIntakeService`. Приём (`JpaTransactionStore.saveIfAbsent`) блокировку **не** берёт и
   не должен: он только вставляет строку `PENDING`, в накопленную сумму не входящую. Возврат вызова
   `ensurePeriodLock` в приём ставит `POST /transactions` в очередь за расчётом того же
   «счёт + категория + месяц» и удерживает при этом соединение пула, то есть отнимает соединение у
   расчёта, который стоит за блокировкой. При неудачном соотношении пула и параллелизма ожидание
   выедает пул целиком, и страдает уже всё остальное — приём, чтение лимитов, — не расчёт.
   Регресс-тест: `ConcurrentSettlementIntegrationTest#intakeDoesNotWaitForSettlementPeriodLock`.
7. **Внешний API не вызывается в потоке приёма транзакции.** `POST /api/v1/transactions` отвечает
   `202` и сохраняет `PENDING`; расчёт — отдельно. Это требование ТЗ о сохранности данных.
8. **Курс добывается вне транзакции БД.** `TransactionIntakeService.settle` **не** помечен
   `@Transactional`: внешний вызов под блокировкой периода держал бы соединение PostgreSQL на всё
   время ожидания сети. Сеть — в `ParallelRateResolver`, запись — в `SettlementApplier`. Нельзя вешать
   `@Transactional(readOnly = true)` на `settle`: транзакция присоединится к транзакции `apply` с
   `REQUIRED` и унаследует её режим, после чего `FOR UPDATE` упадёт с «cannot execute SELECT FOR
   UPDATE in a read-only transaction».
9. **Параллельный расчёт двухфазный.** `settlePending` сначала параллельно получает курсы
   (`ParallelRateResolver`, дедупликация по паре «валюта + дата»), затем параллельно применяет их
   (`SettlementApplier`, своя транзакция на транзакцию). Переносить сетевой вызов внутрь расчёта
   нельзя — это откатывает смысл п.1*. Разные периоды и счета считаются параллельно, операции одного
   `(счёт, категория, месяц)` остаются последовательными: это цена корректности лимита.
10. **Число одновременных транзакций ограничено** `exchange.settlement.parallelism` (по умолчанию 16)
   через `BoundedVirtualThreadExecutor`. Без границы широкая пачка `PENDING` на разных счетах
   открыла бы столько соединений, сколько операций, и исчерпала пул PostgreSQL. Новый код, который
   занимает соединение БД или ходит в сеть на каждую операцию, обязан идти через этот пул.
   Параллелизм не может быть больше размера пула: задачи расчёта держат соединение, пока ждут
   блокировку периода (п.6), поэтому `SettlementPoolGuard` требует `parallelism + 4 ≤ maximumPoolSize`
   и поднимает контекст с `IllegalStateException`, если запас для приёма и чтения не остался.
   Проверка идёт по фактическому `HikariDataSource`, а не по YAML: не-Hikari пул не оценивается.
   Меняешь дефолт параллелизма или минимальный размер пула — проверь инвариант, иначе расчёт
   останется верным, но выест пул и уронит приём.
   Смена лимита идёт через тот же пул: `LimitCommandService.createLimit` не транзакционный, а
   транзакционная работа уходит в `LimitChangeApplier` через `settlementExecutor`. Пока идёт
   пересчёт флагов периода, соединение занято и ждёт блокировки, и на потоке HTTP-запроса число таких
   ожиданий ничем не ограничено: волна смен лимита выедала бы пул целиком, и первыми от этого
   переставали работать приём операций и чтение лимитов. В пуле задача сначала дожидается очереди и
   только потом берёт соединение. Пересчёт при этом остался в той же транзакции, что и запись
   лимита: разносить их значило бы показать клиенту промежуточное состояние «новый лимит — старые
   флаги», а при сбое пересчёта лимит остался бы записанным навсегда. Регрессия:
   `LimitCommandServiceTest`.
11. **Ошибки — ProblemDetail (RFC 9457).** `400` — формат и Bean Validation, `404` — нет ресурса,
    `422` — формат верен, но значение неприемлемо. Не добавляй свой формат ошибок. В `errors`
    поле называется JSON-именем из `@JsonProperty`, а не Java-компонентом: клиент шлёт
    `account_from` и не знает слова `accountFrom`, а исправлять нужно присланное
    (`ProblemDetailExceptionHandler#jsonFieldName`, регрессия
    `ApiErrorContractIntegrationTest#validationErrorNamesFieldAsClientSendsIt`).
12. **Одно правило проверяется в одном месте.** Точность суммы проверяет `@Digits` на DTO; если
    сервис проверяет то же самое ещё раз, это дублирование.
13. **Секреты только через переменные окружения.** В конфигурацию коммитится `${RATES_API_KEY:}`,
    а не значение.
14. **Свойство, которое никто не читает, — ошибка.** На такое уже наступали: `exchange.rates.provider`
    был задокументирован, но ни один бин его не проверял, и подмена провайдера молча игнорировалась.
    Теперь выбор провайдера сделан `@ConditionalOnProperty` на бине в `RateClientConfig`. Добавляя
    настройку, либо читай её в коде, либо не добавляй. Обратная сторона того же правила: значение,
    объявленное в трёх местах, — это тоже декорация. `retry-delay` держался в `application.yaml`,
    в record `SettlementProperties` и в `@Scheduled(fixedDelayString = ...:5s)`, и правило
    нарушалось трижды: два «мёртвых» чтения давали впечатление, что настройка работает, а паузу
    планировщика можно было поменять в yaml и не заметить. Теперь `@Scheduled` читает
    `${exchange.settlement.retry-delay}` без своего default, а `SettlementProperties` содержит
    ровно те поля, которые читает код (`maxAttempts`, `batchSize`, `parallelism`); `retry-delay` и
    `processing-enabled` потребляются аннотацией и условием создания бина, поэтому в record не
    дублируются. Тот же запрет касается констант: размер пачки планировщика пришёл в конфигурацию
    именно потому, что пачка на 100 транзакций при параллелизме 16 держит соединения PostgreSQL
    вчетверо дольше пачки на 25. Регрессия: `PendingSettlementSchedulerTest`.
15. **Приём, запись курса и счётчик попыток рассчитаны на конкуренцию.** Параллельная дорасчётка
    пишет и курсы, и транзакции одновременно. Отсюда три правила: приём операции — нативный
    `INSERT ... ON CONFLICT (id) DO NOTHING` (`TransactionStore.saveIfAbsent`), запись курса —
    нативный `ON CONFLICT DO UPDATE` с `COALESCE` в `SET`, засчётка попытки — нативный `UPDATE` с
    `settlement_attempts = settlement_attempts + 1` и `CASE` на переход в `FAILED`
    (`JpaTransactionStore.registerUnresolvedAttempt`). `save()` на конфликте упадёт, а инкремент,
    сделанный в Java, теряется: два конкурентных дорасчёта читают одно значение и пишут одно и то же
    увеличенное, счётчик зависает, а `FAILED` при `max-attempts: 1` не наступает никогда. Тот же
    `UPDATE` не трогает уже рассчитанную транзакцию (`status <> 'RATE_RESOLVED'`): перевод обратно в
    `FAILED` при заполненных курсе и сумме нарушил бы `ck_expense_tx_resolved_consistent`. Регрессия:
    `SettlementFailureIntegrationTest#concurrentAttemptsAreAllCounted`.
    Взятие пачки тоже конкурентно: `TransactionStore.claimPending` берёт строки `SELECT ... FOR UPDATE
    SKIP LOCKED` и засчитывает им попытку в той же транзакции. Без этого две реплики сервиса (или два
    прохода планировщика) разбирали одну пачку дважды: счётчик попыток рос вдвое быстрее, транзакции
    достигали `FAILED` раньше срока, а внешний API получал двойные платные вызовы. Попытка
    засчитывается при взятии, а не по исходу расчёта: сбой между взятием и расчётом не оставит
    транзакцию с незасчитанной попыткой. Отменённый дорасчёт попытку не засчитывает — счётчик
    снимается отдельным `UPDATE` (`TransactionStore.releaseClaim`), иначе при `max-attempts: 1`
    остановка сервиса переводила бы транзакции в `FAILED`. Регрессии:
    `SettlementFailureIntegrationTest#concurrentClaimsDoNotOverlap`, `#claimCountsAttemptAtOnce`.
16. **Ошибки протокола — ProblemDetail.** `ProblemDetailExceptionHandler` объявлен с
    `HIGHEST_PRECEDENCE` и перехватывает `Exception`, из-за чего обходит
    `DefaultHandlerExceptionResolver`: без явных `handle*`-методов 400/404/405/406/415 от Spring MVC
    превращаются в 500. Добавляя эндпоинт, подумай, какой код он отдаст на чужой метод и неверный
    путь, и проверь это в `ApiErrorContractIntegrationTest`.
17. **Попытка дорасчёта засчитывается при любом сбое.** `settlement_attempts` растёт и когда курс не
    пришёл, и когда расчёт упал: иначе `findPending` возвращает транзакцию каждые `retry-delay`
    секунд, счётчик навсегда остаётся нулём, а `FAILED` недостижим — до перезапуска сервиса. Именно
    так было: счётчик жил только в ветке «курс недоступен», а упавший расчёт логался `WARN` и уходил
    в бесконечный ретрай. Оба пути (`settle` и `settlePending`) считают попытку в
    `TransactionIntakeService.registerFailedAttempt`; ошибка расчёта логируется `ERROR`, недоступность
    курса — `WARN`, потому что первое требует внимания. Исключение при этом не теряется: в ручном
    дорасчёте пробрасывается вызывающему, в пачке гасится на одну задачу. Счётчик растёт
    атомарно (п.15), и метод сообщает, засчитана ли попытка: `false` означает, что транзакцию уже
    посчитал кто-то ещё, и логи не должны утверждать «попытка засчитана».
    Правило «при любом сбое» относится к сбоям расчёта, а не к отмене: **прерванный поток попытку не
    засчитывает** (`RateCallCancelledException`), потому что до расчёта дело не дошло. Отмена
    рождается в `RetryingCaller` на `InterruptedException` при паузе перед повтором и обязана
    пробрасываться наружу, а не превращаться в `null` «курс недоступен»: `InterruptedException`
    раньше глушился, цикл доводил попытки до конца, и остановка сервиса выглядела как сбой биржи —
    при `max-attempts: 1` один перезапуск переводил нормальные транзакции в `FAILED`. Следствие для
    обработчика: `registerFailedAttempt` проверяет отмену сам, повторно проверять её в вызывающем
    коде не надо, а лог отмены — `INFO`, не `ERROR`: никто не должен срочно чинить то, что
    остановили намеренно. В пакетном пути отмена не только не засчитывается, но и снимает попытку,
    уже засчитанную при взятии пачки (п.15): без этого прерванный поток оставлял бы «засчитанную»
    попытку, и тот же перезапуск переводил бы транзакции в `FAILED`. Регрессии:
    `SettlementFailureIntegrationTest#cancelledSettlementKeepsAttemptUncounted`,
    `RetryingCallerTest`.
18. **Одиночный дорасчёт считает попытку на всех исходах, а не только на последнем шаге.** Правило 17
    пережило один путь: `resolveUsdRate` вызывался прямо в `settle`, и исключение из него выходило
    раньше ветки подсчёта, поэтому сбой получения курса на нашей стороне (например, нарушение
    CHECK при записи курса в кэш — по п.3 он обязан выходить наружу) попытку не тратил. Ровно тот
    баг был у батча, чинили только его, и одноэндпоинтный путь жил: `findPending` возвращал
    транзакцию вечно, `FAILED` был недостижим именно там, где дорасчёт запускает человек.
    Возвращаемое значение берётся из БД **после** попытки (`reloaded`): снимок до попытки утверждал
    бы `PENDING` для транзакции, которая попыткой только что достигла `FAILED`, и вызывающий счёл бы
    её расчётной. Регрессии:
`SettlementFailureIntegrationTest#manualSettleCountsAttemptWhenRateResolutionFails` (падает с
     `attempts: 0`) и `#manualSettleReturnsStateAfterAttempt` (падает с `PENDING` вместо `FAILED`).
19. **Досчёт начинается по событию приёма, а не по таймеру.** Плановый проход каждые `retry-delay` —
    страховка, а не темп: без досчёта по событию клиент, отправивший операцию и сразу запросивший
    `GET /limits/exceeded`, уходил бы с ответом «превышений нет» на полминуты после приёма. Событие
    `TransactionAccepted` публикуется внутри транзакции `accept` и обрабатывается **после** её
    фиксации (`AFTER_COMMIT`): до коммита строки в базе нет, и проход её бы не нашёл. Обработчик
    (`PendingSettlementScheduler.requestPass`) только ставит флаг и кладёт задачу в
    `settlementExecutor` — на потоке HTTP-запроса не происходит ни запроса к сети, ни соединения с
    БД (иначе волна приёмов съедала бы пул, как в п.6 и п.10). `@EnableAsync` для этого не нужен и
    удалён: задачи и так уходят на виртуальные потоки пула.
    Проход всегда один: параллельные проходы не опасны для данных (`claimPending` не даст взять
    строку дважды), но дедупликация курсов по паре «валюта + дата» видит только свой проход, и два
    прохода отправили бы платные запросы дважды. Взамен проход, увидевший запрос во время работы,
    делает ещё один круг — без этого транзакция, принятая после взятия пачки, ждала бы планового
    прохода (в бою 5 секунд, в тесте с `retry-delay=1h` — час, и тест на досчёт по событию падал бы
    по таймауту). Порядок флагов обязателен: `passRequested` проверяется и снимается так, что запрос
    либо увидит занятый `passRunning` и заставит текущий проход сделать ещё круг, либо увидит
    свободный и запустит проход сам. В очереди пула не более одной задачи (`kickQueued`), иначе пачка
    приёмов плодила бы пустые задачи; флаг снимается **до** прохода, иначе приём, пришедший во
    время расчёта, остался бы без прохода. Регрессии:
    `SettlementKickIntegrationTest#acceptedTransactionIsSettledWithoutWaitingForTheScheduledPass`
    (падает по таймауту ожидания) и `#burstOfAcceptedTransactionsIsSettledCompletely`
    (падает, если проход не делает второй круг), плюс
    `PendingSettlementSchedulerTest#requestDuringRunningPassIsSatisfiedByAnExtraRound`.
20. **Дорасчёт вручную доступен через API.** Статус `FAILED` означает «требуется ручной расчёт», и
    такой путь обязан существовать в эксплуатации: `POST /api/v1/transactions/{id}/settle` вызывает
    `TransactionIntakeService.settle` и отвечает `200`, если транзакция рассчитана, `202`, если курс
    всё ещё недоступен (попытка потрачена, транзакция осталась `PENDING`), и `404`, если операции
    нет. Один код для обоих состояний заставлял бы клиента смотреть в тело и гадать, посчитано или
    нет. Эндпоинт считает попытки по правилам пп. 17–18, то есть повторный вызов на
    `FAILED`-транзакции честно расходует попытку; запрещать это нельзя — иначе ручной досчёт был бы
    недостижим ровно там, где он нужен. Регрессии:
    `ExpenseApiIntegrationTest#manualSettleRecoversFailedTransaction`,
    `#manualSettleReportsPendingWhenRateIsUnavailable`,
    `#manualSettleOfUnknownTransactionIsNotFound`.

## Решения, принятые сознательно

Не «забыто», а выбрано. Не меняй без новой причины.

- **Логирования HTTP-обмена (Logbook) нет.** Актуальная версия (3.12.x) собрана под Spring Boot 3,
  проект на Boot 4.1.1, где `WebMvcAutoConfiguration` больше не поставляется
  `spring-boot-autoconfigure` и автоконфигурация Logbook не поднимется. Свой фильтр писать не
  стоит: он повторит то, что делают `RestClient` и Micrometer. Подключится само, когда выйдет
  версия под Boot 4.
- **Даты операций не ограничены «не в будущем».** В ТЗ этого требования нет, а банк присылает
  операции с датой в будущем; отклонение означало бы потерю данных. Согласованность флагов для
  таких операций обеспечивает пересчёт периода (п.5).
- **Отражения в коде нет.** Публичные методы домена, которые читает только один класс, — нормально;
  искусственный «слой отражений» ради чек-листа ТЗ удалял бы типобезопасность и ломался бы при
  `--release`-сборке.
- **Лимит по умолчанию виден в `GET /limits`, но без идентификатора.** Счёт, у которого есть расход в
  текущем месяце, но нет лимита этой пары **в этом месяце**, получает в ответе строку с
  лимитом по умолчанию (1000 USD, момент установки — первый день месяца) и своим расходом. Без неё
  клиент видел флаги превышения, посчитанные по этому лимиту, и пустой список лимитов. Строка
  добавляется второй веткой `UNION ALL` в `findLimitsWithSpentAmount`, а не в Java: остаток и расход
  считает SQL, вторая реализация разошлась бы с ней (см. следующий пункт). `limit_id` такой строки —
  `null`: лимит не хранится, и выдуманный идентификатор ссылался бы на несуществующую запись. Пары
  без расхода в периоде дефолтной строки не получают — показывать лимит, который ничего не
  ограничивает, незачем.
- **Идентификатор операции не подменяется.** Непустой `transaction_id` не-Uuid отклоняется с `400`
  на границе (`@Pattern` в `TransactionRequest`), а `TransactionIntakeService.resolveTransactionId`
  больше не ловит `IllegalArgumentException` и не выдаёт случайный UUID. Ключ идемпотентности,
  который меняется на каждой доставке, обесценивает саму доставку: потерянный ответ приводит к
  повторной отправке, а та создаёт вторую запись и удваивает расход месяца. Пустое поле и его
  отсутствие означают «идентификатора нет», и тогда UUID генерирует сервис. Регрессии:
  `ExpenseApiIntegrationTest#nonUuidTransactionIdIsBadRequest` и
  `#emptyTransactionIdIsAcceptedAndGenerated`.
- **Одна реализация расхода и остатка — SQL.** Не возвращай `LimitCalculator.remaining` и подобное:
  вторая реализация того же правила разойдётся с нативным запросом `findLimitsWithSpent`, и клиент
  увидит остаток, не согласующийся с `limit_exceeded`.

## Тестовые конвенции

- Интеграционный тест наследует `AbstractIntegrationTest` и не поднимает свой контейнер.
- Операции для проверки лимитов — в `USD`, тогда внешний API не участвует и результат не зависит
  от заглушек.
- Идентификаторы транзакций — последовательные (`ID_SEQUENCE`): при равном времени порядок
  определяется сравнением `id`, случайные UUID сделали бы тест недетерминированным.
- Расчёт в тесте вызывается явно: `intakeService.settle(pending.id())`. Никаких `Thread.sleep`.
- Проверяешь пересчёт флагов — читай `limit_exceeded` из БД через `jdbcTemplate`, а не возвращённое
  значение расчёта.
- Тестовый профиль выключает фоновую дорасчётку (`exchange.settlement.processing-enabled=false`):
  иначе результат зависел бы от фоновой задачи, запущенной приёмом. Отсюда исключение с ручным
  вызовом расчёта — оно распространяется и на досчёт по событию приёма (п.19).
- Проверка асинхронного поведения — единственное место, где ждать приходится: дедлайн в цикле
  опроса вместо фиксированной паузы (`SettlementKickIntegrationTest.await`). Такой тест поднимает
  второй контекст (`processing-enabled=true`, `retry-delay=1h`) — иначе рассчитать транзакцию мог бы
  планировщик и проверка ничего бы не доказывала.

## MCP

Подключение к локальной БД описано в README, раздел «MCP». Две ловушки, на которые уже наступали:
сервер `@modelcontextprotocol/server-postgres` принимает подключение **URL аргументом командной
строки** и не читает `PGHOST`/`PGUSER`/`PGPASSWORD` из окружения, а у instruments разный синтаксис
подстановки (Cursor — `${env:VAR}`, Codex — `env_vars`, Claude Code — `${VAR}`). Правя конфиги,
проверяй MCP настоящим клиентом, а не чтением JSON: конфиг без URL аргумента выглядит безобидно и
молча не подключается.

## Скиллы

В `.agents/skills/` лежат скиллы для типовых задач: `limit-testing`, `rate-provider`,
`db-migration`. Формат — открытый стандарт Agent Skills, одинаковый для Codex, Cursor, Claude Code и
Copilot. Прочитай подходящий скилл, прежде чем писать код в этих областях.

## Чего не делать

- Не менять семантику расчёта лимитов без нового теста, который её фиксирует.
- Не отключать WireMock или Testcontainers, «чтобы тест прошёл быстрее».
- Не добавлять индексы без комментария, какой запрос они ускоряют: индексы стоят на записи, а
  лишние съедают время вставки транзакций.
- Не хардкодить лимиты, курсы, таймауты и URL: всё через `@ConfigurationProperties`.
- Не коммитить `.idea/`, `target/`, файлы с секретами.
